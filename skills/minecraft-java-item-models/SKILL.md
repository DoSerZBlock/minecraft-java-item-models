# Minecraft Java 物品模型

依使用者指定的世界觀、版別與版本，交付可編輯的 Blockbench 專案、貼圖及可直接載入的資源包。這份流程針對「物品」；遇到可放置方塊或生物時，先確認其實際資產類型，再使用對應格式。

## 任務合約與迭代

新建模型或修改結構時，先讀 [施工規範](references/AI_MODELING_SPEC.md)，再讀 [顯示校準規範](references/DISPLAY_CALIBRATION.md)。既有專案的任務規格和已認可畫面是優先依據；若專案尚無規格，從 [任務模板](assets/templates/MODEL_TASK.template.toml) 建立工作區的 `tasks/<asset>.task.toml`，填入版本、bounds、parts、budget、texture、display、outputs 與 QA。純顯示或光照修正只補足與該修改相關的合約。

執行 `python <本 skill 的絕對路徑>/scripts/validate_task.py <任務檔>`；需要 Python 3.11 以上。隨附驗證器檢查部分 TOML 結構與幾何預算，不會驗證變換後的 bounds、Java 旋轉限制、顯示政策或產出檔案是否存在，這些須另行核對。

修改 `.bbmodel` 前先檢查使用者目前版本的專案或 seed，保留格式 metadata 與未知欄位。隨附範例是既有 Java seed，需確認與目標 Blockbench 版本相容。新建模型先交付 Pass A blockout，查看必要視角、記錄可量測缺陷、修改後重看，再進入結構和表面精修；沒有渲染或遊戲環境時，把對應 QA 標為 pending。

顯示校準先處理任務的 primary context，依 rotation → translation → scale 調整，GUI 另作構圖。單一視角問題只改該 context；若多數視角證明基礎幾何有問題，回到結構修正，然後重查所有已通過的視角。[顯示缺陷模板](assets/templates/DISPLAY_DEFECTS.template.md) 可用於記錄。

## 開始

1. 確認目標 Java 版本、物品用途、外觀參考與交付方式。使用者指定既有世界觀或提供資料來源時，先讀其權威設定，釐清通用規則與國家／流派特徵；把設定事實和新提出的造型方案分開。接續修改時，先檢查現有 `.bbmodel`、貼圖、資源包和遊戲截圖，記下哪些視角已獲使用者認可。
2. 確認該版本的資源包格式與物品模型語法。以官方版本資訊為準；不要把範例中的 26.2 數值套到其他版本。
3. 選擇原版物品作為遊戲行為基底。若使用者只要特定物品換外觀，使用自訂 `minecraft:item_model`，附取得指令，讓一般原版物品照常顯示。

## 建模與打包

- 保留可編輯 `.bbmodel` 和 PNG 貼圖。將模型轉成 Java 物品模型時，檢查元素邊界、旋轉軸與角度、每面的 UV、貼圖路徑，以及預期的顯示縮放。UV 要依貼圖實際解析度換算。
- 任務明確允許 `allow_display_specific_geometry_override = true`，且物品欄與手持視角確實需要不同幾何時，分別輸出 GUI 與 held 模型，並用 `minecraft:select` 的 `minecraft:display_context` 將第一、第三人稱導向 held 模型，其餘情境回退 GUI 模型。參考 [26.2 歷史校準案例](references/gray-sun-26.2.md)。
- 修改已認可的模型時，只動目標視角。把顯示旋轉與位移放在該視角的 `display` 參數中；任務允許獨立手持幾何且需要更換刃側時，作為結構修正修改手持模型的刀身，保留握柄、護手與物品欄模型，之後重新檢查全部受影響視角。
- 以小幅變更迭代姿勢，根據遊戲截圖檢查握柄是否穿過手掌、刀刃朝向、刀尖方向和畫面占比。「刀刃朝上／下」與「刀尖朝上／下」是不同的調整，從圖片判斷或在必要時釐清。

## 結構位置與對稱

1. 建模、檢查或修改模型時，先依任務規格與設計意圖列出對稱平面／軸、成對部件和置中部件。未指定非對稱設計的成對結構，必須檢查對稱；刻意非對稱的部件須記錄範圍與用途，保留其設計，同時檢查其餘應對稱的結構。
2. 以套用元素與父群組旋轉、樞軸及格式適用的縮放後的實際幾何進行比較。檢查鏡射後的頂點／表面、位置、尺寸、朝向與中央部件的偏移；只比較原始 `from`／`to` 或中心點不足以證明對稱。依模型格式計算變換，勿把 Euler 角符號反轉當成通用鏡射算法。
3. 檢查相鄰結構的接合、間隙、穿插和共面閃爍，確認裝飾、支架與主體的位置自然。設計指定的懸浮、嵌入和非對稱配置應保留；意圖無法確認時，記錄疑點，先完成可確認的修正。
4. 記錄每組檢查結果、最大偏差、模型單位與採用的容差；容差以任務規格為準，未指定時採用符合幾何精度的容差並說明依據。列出正面、背面、側面及需要的斜視圖證據，區分數值檢查、離線投影、Blockbench 截圖與遊戲實測。
5. 修改前備份；選定正確的一側或設計基準作局部修正，保留既有名稱、UUID、未知欄位、貼圖、UV 與已認可的顯示設定。結構修改後重新檢查全部應對稱部件、接合位置與先前通過的視角；完成條件是規格容差內通過，或清楚記錄尚未通過及無法驗證的項目。

## 物品欄光照

- 建模、匯出及整合資源包時，檢查物品定義實際引用的全部模型之有效 `gui_light`，包含父模型繼承、GUI／手持分支、動畫幀及各段拉弓。一般物品圖示以 `front` 為基準；刻意採用方塊式側光的設計，依任務規格保留並記錄理由。
- 物品欄偏暗時，先比對光照模式與貼圖原色，再決定是否調整材質。對既有 Java 專案，依當前 Blockbench 原生格式同步 `front_gui_light`；匯出的 Java 模型同步 `gui_light`，並確認可編輯模型、獨立包與最新版整合包一致。
- 光照修正保留幾何、UV、貼圖、物品選擇器及使用者展示位置／旋轉／縮放。動畫和拉弓狀態使用一致的預期光照，避免切換時忽明忽暗；整合時確認採用已認可的最新版，舊包的缺省設定可能覆蓋新設定。
- 分開記錄設定檢查與實際畫面驗收。`front` 不代表真正自發光；遊戲亮度仍須載入後確認，未執行時標示待實測。

## 驗收與交付

- 檢查 ZIP 可讀、`pack.mcmeta` 與目標版本一致、物品定義能解析到正確模型、貼圖路徑有效、元素與 UV 在允許範圍內。對已認可的視角，比較原模型或截圖，避免回歸。
- 靜態檢查無法證明實際握持效果；能進遊戲時直接檢查，否則提供資源包讓使用者載入並以截圖回饋。替換舊 ZIP 後可在遊戲中按 F3+T 重新載入。
- 交付資源包、可編輯模型、貼圖與簡短使用說明；若使用自訂物品模型，附可複製的 `/give` 指令。
